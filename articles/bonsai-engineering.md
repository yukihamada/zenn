## 何を知りたかったか

LLMを業務処理へ組み込むと、説明が上手いことと、そのままパース・実行できることは別です。請求集計の `null`、JOINで水増しされる請求額、不要なツール呼び出し、HTTP 200なのに本文が空、といった失敗を確かめました。

筆者は測定経路の **teai.io の開発者**です。この記事は自作API経由の小規模な合成課題の観測であり、独立第三者の評価や汎用性能ランキングではありません。推論モデルの重みを独立認証したものでもありません。

対象は `prism-ml/ternary-bonsai-2-27b`、`upstage/solar-mini4`、`z-ai/glm-5.3-flash`。旧12課題×2回の実験に続き、**別実験として18課題×3回**を測定しました。出題が曖昧な1課題は全モデルから事後除外し、主要集計は17課題×3回です。

## 結果を先に

| モデル | 成功/予定 | 未確認 | フェンスだけ除去 | 全応答p50 / p95 |
|---|---|---|---|---|
| Ternary Bonsai 2 27B | 50/51 | 1 | 50/51 | 7.02 / 35.44秒 |
| Solar Mini4 | 35/51 | 0 | 35/51 | 6.29 / 26.53秒 |
| GLM 5.3 Flash | 37/51 | 0 | 46/51 | 1.73 / 3.39秒 |

Bonsaiの未確認1件は、測定プロセス自体の時間制限で応答を記録できなかったものです。誤答として断定せず、料金予約を残して再送しませんでした。記録済み主要50試行はすべて成功。同じ課題・ラウンドを3モデルから除いた対応あり比較では **50/50、34/50、36/50** です。

レイテンシは除外課題を除く**リクエスト単位**で、Bonsai 52件、Solar/GLM各54件。ツール後続応答、誤答、空回答を含みます。未記録1件は含まず、ツールの一連の処理時間でもありません。p50は中央値、p95はnearest-rankです。

## 1. JSONはパースできれば合格、にしない

型と値の完全一致で採点しました。`false` と `0`、`null` と `0`、整数と文字列を区別し、余分なキー、重複キー、NaN/Infinityを拒否します。Pythonでは `False == 0` が真なので、型も見る必要があります。

```python
def equal(a, b):
    if type(a) is not type(b):
        return False
    if isinstance(a, dict):
        return a.keys() == b.keys() and all(equal(a[k], b[k]) for k in a)
    if isinstance(a, list):
        return len(a) == len(b) and all(equal(x, y) for x, y in zip(a, b))
    return a == b
```

主要集計はコードフェンスも除去しません。別列だけ外側の単一フェンスを除いて再採点し、形式違反と中身を分けました。説明文の除去、値の修正、型変換はしていません。通常回答には `finish_reason=stop` も要求しています。

GLMの14失敗は**フェンスのみ9、値または型の不一致4、不正JSON 1**。フェンス除去だけで37→46/51になりました。つまり厳密成功率だけから「14件の内容が誤り」と解釈してはいけません。

## 2. SQLは3種類×8状態で実行

スキーマは顧客、請求、入金の3テーブル。課題は請求・入金集計、最高額請求の選択（同額なら最小ID）、未払い一覧です。各生成SQLを8種類のSQLite状態で検査しました。

- 空テーブル、請求のない顧客
- 同額でも別の請求書、1請求への複数入金
- 過払い、0円、同額タイ、疎なID、大きな整数

たとえば請求100が2枚、片方に30と20の入金がある場合、素朴なJOIN後のSUMは請求を複製します。`SUM(DISTINCT amount)` では今度は同額の別請求が消えます。顧客ごとの期待値は独立したPython計算で作り、SQLの列名・行・順序まで照合しています。

実行はSQLiteのauthorizerで読み取りに限定し、実行ステップに上限を設けました。8状態すべての成功で1試行成功です。**8回独立に生成したのではなく、同じSQLに8状態を当てたもの**で、3課題は同じスキーマを共有します。

SQL成功はBonsai 9/9、Solar 1/9、GLM 9/9でした。ただしSolarの失敗は空回答です。「SQLが書けない」ではなく、今回の設定と経路で実行可能な回答を得られなかった、と読むべきです。

## 3. ツールを呼ばない判断も測る

`tool_choice=auto` で、以下を分離しました。

1. 注文IDあり：`lookup_order` を正しい引数で1回呼び、模擬結果を渡した後のJSONも確認
2. 確認済みデータあり：ツール不要、呼び出し禁止
3. 注文IDなし：勝手にIDを作らず、`{"needs":"order_id"}` を返す

呼び出し＋後続回答で1試行。実注文や外部サービスへのアクセスはありません。成功はBonsai 8/9（別に未確認1）、Solar 9/9、GLM 7/9です。

## 5. 空のHTTP 200を成功と数えない

Solarの主要16失敗は、すべて本文が空で `completion_tokens=2048` でした。出力上限や推論処理との関係が疑われますが、推論内部の内訳は未確認です。上限を増やした比較は実施していません。

料金とトークンはproviderのusageから計算しており、表示本文の文字数ではありません。同じ `max_tokens` を指定しても、各モデルの推論・出力への割当が同じとは限りません。

## 6. 初回本文の到着時間を「モデルのTTFT」と呼ばない

整数列1〜10と1〜120を各3回ストリームで要求。クライアント送信から最初の非空 `delta.content` までを測りました。roleイベントやkeepaliveは除外しています。

| 指定モデル | 課題 | 初回本文p50 | 本文あり |
|---|---|---|---|
| Ternary Bonsai 2 27B | stream_short | 3.46秒 | 3/3 |
| Ternary Bonsai 2 27B | stream_long | 27.73秒 | 3/3 |
| Solar Mini4 | stream_short | 18.96秒 | 1/3 |
| Solar Mini4 | stream_long | — | 0/3 |
| GLM 5.3 Flash | stream_short | 1.60秒 | 3/3 |
| GLM 5.3 Flash | stream_long | 4.37秒 | 3/3 |

**本文あり13応答はすべて本文イベント1回**、残る5応答は0回でした。全18件で応答 `model` は指定IDと一致しましたが、`x-teai-route` がなく経路・fallbackは未確認です。元採点は `identity_unverified` のまま残しています。

したがってこれは「指定IDごとのteai経由の初回本文到着時間」です。ネットワーク、ゲートウェイ、バッファリングを含み得て、提供元ネイティブのTTFTや逐次トークン生成速度ではありません。短い課題は空白指定が曖昧なので、厳密文字列一致を品質順位には使いません。

## 7. 出題側の欠陥と、実験の限界

`access_precedence` は「JSON配列」とだけ書き、文字列配列かオブジェクト配列かを指定していませんでした。正しい判定を含むオブジェクト配列を誤答にする採点だったため、**結果を見た後に全モデルの9試行を除外**しました。元採点は全モデル0/3。除外前は50/54（未確認1）、35/54、37/54で、元回答と元採点も公開しています。

これは事後判断であり、事前登録と称してはいません。また算術課題 `money_rounding` の期待値は実行前の独立検算で2129に訂正しています。

固定条件は2026-09-27、temperature=0、max_tokens=2048、推論設定は提供元既定、並行数1、100秒タイムアウト、自動再試行0。モデル順は課題・ラウンドで循環させました。単一日・単一経路・自作課題の3反復なので統計的優位は主張しません。3反復を3倍の独立問題と数えず、他の業務への一般化や学習データ混入も未確認です。

非ストリームの169応答はAPIが返すモデルID、経路のserved、fallback_depth=0の一致を確認。これはモデル重みの独立認証ではありません。

追加分の既知料金推計は **¥4.4709**、未確認1件は5円の予算予約を保持。旧実験を含む既知推計は¥6.4674、不明4件を含む予算計上は¥26.4674（450円実行上限）です。保存単価とusageからの推計で、確定請求額や請求上限の保証ではありません。

## 実装に持ち帰ること

型まで検査する、SQLは重複や欠損を含めて実行する、空の200を成功にしない、ツール不要時も評価する。そして「全応答時間」「最初の本文」「提供元TTFT」を混同しない。

今回の数字はモデルを一列に並べるためではなく、**自分の仕事で何を成功と数えるかを実装するため**の材料です。
